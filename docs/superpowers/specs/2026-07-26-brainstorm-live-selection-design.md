# Brainstorm Canvas — the agent sees your live board selection

**Date:** 2026-07-26
**Status:** Implemented and verified end-to-end

Supersedes `2026-07-26-brainstorm-agent-selection-context-design.md`, which
scoped this down to a documentation-only change ("describe the elements in
words and the agent resolves it"). That wasn't good enough in practice: on a
dense board the user selects a cluster and asks "explain these" / "make these
green", and describing them in prose defeats the point of selecting. The
frontend-patch risk that justified descoping turned out to be manageable once
the patch was scoped to two anchors instead of a component rewrite.

## Problem

The agent could read the whole board (`describe_scene`, `query_elements`) but
had no notion of what the user had **selected**. Two independent reasons:

1. The MCP server shipped a `sceneState.selectedElements` Set that was
   initialised once and **never populated** — dead code. `get_resource("scene")`
   dutifully reported `selectedElements: []` forever.
2. Selection (`appState.selectedElementIds`) lives in the board's Excalidraw
   instance, in a **separate Tauri window on a separate origin** from the chat
   panel (WKWebView partitions cross-origin iframe storage, so the board was
   deliberately split into its own `WebviewUrl::External` window). Nothing ever
   carried it across that boundary.

So the agent's honest answer was "there's no `get_selected_elements` call and
no selection concept I can reach" — which is what the user saw.

## Approach

Mirror how board *edits* already cross the window boundary (frontend →
`POST /api/elements/sync` → canvas server → WS broadcast), but for selection.

```
board window (Excalidraw)                canvas server            chat window / agent
  onChange fires
  → __pushSelection(api)      ──POST──►  /api/selection
     reads appState                       stores + broadcasts
     .selectedElementIds                  `selection_changed`
     (debounced 250ms, diffed)                 │
                                               ├──WS──► chip above composer
                                               ├──GET─► Chat.send() attaches
                                               │        `[selected on board]`
                                               └──GET─► MCP get_selected_elements
```

## Why the frontend is *patched*, not rebuilt

`apps/brainstorm/src-tauri/resources/canvas-server/` vendors
`mcp-excalidraw-server` as **compiled output only** — no frontend source in
this repo. Options considered:

- **DOM scraping** (no rebuild): ruled out. Excalidraw only stamps `data-id`
  on element nodes when built with `MODE === "test"` (a `po()` gate in the
  bundle); in a production build there is no per-element DOM identity to read.
- **Rebuild the frontend** from upstream `1.1.0` or hand-authored source:
  ruled out. The mounted component is not a thin wrapper — it handles WS
  reconnection, element z-order merging, PNG/SVG export
  (`export_image_request` → `/api/export/image/result`), MCP-driven viewport
  control (`set_viewport` → `/api/viewport/result`), and Mermaid conversion,
  with specific `captureUpdate: NEVER | IMMEDIATELY` semantics. Reimplementing
  all of that to add one call risks silently breaking working features.
- **Patch two anchors in the minified bundle**: chosen. The component already
  keeps a ref to the live Excalidraw API (`n`, kept current by
  `useEffect(() => { n.current = e }, [e])`), so `onChange` only needs one
  extra call. Nothing else is touched.

Because `dist/` is a build artifact regenerated by `scripts/stage-server.sh`
(and **not** tracked in git), the patches live in a tracked, idempotent script,
`scripts/patch-canvas-server.mjs`, which `stage-server.sh` now runs after every
copy. Each of the 7 patches asserts its anchor matches **exactly once** and
no-ops when already applied, so an upstream bump fails loudly instead of
silently shipping a half-patched server. The frontend chunk is located by
**content** (which chunk contains the anchor), not filename — Vite emits five
`index-*.js` files and the hashes change.

## Components

| Piece | Change |
|---|---|
| `dist/server.js` (patched) | `currentSelection` state; `POST/GET /api/selection`; broadcasts `selection_changed`. |
| `dist/index.js` (patched) | New `get_selected_elements` MCP tool; `get_resource("scene").selectedElements` now reflects reality instead of always `[]`. |
| frontend bundle (patched) | `onChange` also calls `__pushSelection(n.current)` — reads `selectedElementIds`, debounced 250ms, diffed against last-sent, fails silently. |
| `src/brainstorm/selection.ts` (new) | `fetchSelectedElements`, `formatSelectionBlock`, `summarizeSelectionForChip`. Best-effort: never throws. |
| `Chat.tsx` | Takes `canvasUrl`; user-origin sends prepend a `[selected on board]` block; WS-driven `selectionSummary` for the chip. Watch turns are excluded. |
| `Composer.tsx` | Renders the selection chip above the textarea. |
| `SKILL.md` | Tells the agent the block's ids are ready to use directly, and to call `get_selected_elements` to re-check mid-turn. |

### The label gotcha

Excalidraw does **not** store a shape's label as a `label` property. Once the
board syncs back, the label is a **separate text element** pointing at its
container via `containerId`. Selecting a labelled rectangle therefore selects
only the container, which carries no text — so a naive implementation reports
"rectangle at (220, 260)" and loses "API / backend", which is most of what
makes the context useful. Both the chat-side summariser and the MCP tool
resolve labels across the whole board, and suppress a label child that arrives
alongside its already-selected container (duplicate noise).

## Verification

Driven against a real Excalidraw board in a real browser (CDP), not mocks:

- Shift-clicking two boxes → `/api/selection` reports exactly those two ids.
- Clicking empty space → selection clears.
- `get_selected_elements` through the real MCP server → returns the element
  plus resolved `labelText`.
- A real agent turn given the `[selected on board]` block for one rectangle
  ("make this one green and add a note under it") used the id straight from
  the block, turned **only** that rectangle green, and placed the note in the
  gap above the next box. Confirmed against the board's element list.
- `stage-server.sh` from pristine upstream re-applies all 7 patches; running
  the patch script twice is a clean no-op.
- 80 unit tests pass (14 for `selection.ts`); `tsc --noEmit` clean.

Note the synthetic-input caveat: CDP's `Input.dispatchMouseEvent` does not
reach Excalidraw's canvas handlers in headless Chrome; dispatching real
`PointerEvent`s on the interactive canvas does. That's a test-harness quirk,
not a product issue.

## Known limitations

- Selection is in-memory in the canvas server and resets when it restarts.
- The chip lags a selection change by one WS round-trip. Harmless: `send()`
  re-fetches selection independently, so the prompt is never stale even if the
  chip is.
- Watch/continuous-mode turns deliberately get no selection block — those are
  fixed observation prompts, unrelated to what's selected.
